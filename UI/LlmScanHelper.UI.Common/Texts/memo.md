# LLM Scan Helper — памятка «почему так»

Сканер GGUF + генератор параметров llama-server для V100 + desktop RTX,
безопасного AUTO --fit, MTP и ручного лабораторного режима.
Запуск: LLMScanHelper — WPF-сборка на Windows, Avalonia-сборка на Linux
(те же Core + UI.Common, различается только оболочка). Параметры сохраняются
в settings.json рядом с исполняемым файлом (переносимый режим,
по-модельные профили).

Синтаксис намеренно консервативный: приложение — прямой потомок
LINQPad-скрипта v3, логика формул и флагов сохранена 1:1.

## Единицы

Вся память считается в GiB (1024^3) — так же показывают nvidia-smi и
llama.cpp. Значения VRAM бери из nvidia-smi; если на V100 включён ECC,
nvidia-smi УЖЕ показывает уменьшенный итог — просто вводишь то, что видишь.

## Защита VRAM

В AUTO-режиме резерв теперь НЕ участвует в нашей самодельной формуле слоёв.
Он напрямую превращается в --fit-target: это целевой объём свободной VRAM,
который llama.cpp старается оставить ПОСЛЕ загрузки модели. Для V100 без
Windows достаточно небольшого технологического запаса (по умолчанию 0.50 GiB).
Для RTX, на которой живёт WDDM/рабочий стол/браузеры/IDE, нужен отдельный
большой запас: SAFE=3.00 GiB, BALANCED=2.50 GiB, AGGRESSIVE=2.00 GiB.
Ниже 2 GiB этот UI намеренно не предлагает.

**ВАЖНО:** --fit-target — НЕ аппаратный hard-cap. Runtime рассчитывает
раскладку по свободной VRAM на момент загрузки. Если ПОСЛЕ загрузки открыть
браузер, видео, игру, второй LLM или иное GPU-приложение, новый потребитель
может съесть оставленный запас. Поэтому во время агентного прогона держим
рабочее окружение стабильным: не открываем новые GPU-тяжёлые окна/приложения.
Для новой/подозрительной модели сначала используй профиль V100 ONLY — это
настоящая изоляция RTX (или RTX ONLY, если модель целиком влезает в
десктопную карту).

## Важно для новых Qwen/гибридных архитектур

Формула «веса + обычный KV на каждый слой» уже НЕ является точной:
recurrent/linear-attn слои имеют отдельный state (RS cache), MTP создаёт
дополнительный speculative context, а compute/scratch зависит от -b/-ub и FA.
Поэтому точную раскладку по VRAM в AUTO-режиме делает САМ llama.cpp через
--fit. Этот инструмент больше не притворяется умнее runtime.

## KV-кэш

K и V задаются раздельно (--cache-type-k и -v). q8_0 — хороший рабочий
компромисс. q4_0 экономит память, но на длинном контексте может сильнее
влиять на качество. Если включён Flash Attention и KV квантован, конкретная
сборка llama.cpp должна иметь нужные CUDA FA kernels; при подозрительно
низкой скорости проверь лог и сравни -fa auto/on, а кастомную сборку делай
с GGML_CUDA_FA_ALL_QUANTS=ON.

Строка «Квантование» в инфо о модели — это НЕ этот параметр: она показывает
квантование самой модели из GGUF (general.file_type), а KV-квантование живёт
только в своём комбобоксе (--cache-type-k / --cache-type-v).

## Поведение llama.cpp

**AUTO:** НЕ задаём точный -ngl и НЕ задаём --tensor-split. Передаём
--fit on + отдельный --fit-target для устройств В ТОМ ЖЕ ПОРЯДКЕ, что и
--device. Runtime сам выбирает раскладку по реально свободной VRAM, включая
KV/RS/compute/speculative context.

**MANUAL:** --fit off, -ngl задаётся явно, а --tensor-split X,Y — это
ПРОПОРЦИИ распределения offload, НЕ точное количество слоёв. split-mode
layer — правильный дефолт для V100 + RTX на разных PCIe; tensor —
экспериментальный и требовательнее к меж-GPU связи.

**MTP:** модели могут хранить дополнительный блок как blk.N при
N == block_count, а тензоры часто содержат nextn/mtp. Программа их
детектирует, но размер MTP используется только для информации. Реальный
расход памяти MTP больше размера его тензоров, поэтому в AUTO оставляй
нормальный --fit-target. Дефолты llama.cpp для MTP: draft max=3,
draft min=0. min никогда не должен быть > max.

**Reasoning** детектим по чат-шаблону (enable_thinking/reasoning) и тегам.
Режим — 3-позиционный (ТЗ2): on → --reasoning on, off → --reasoning off,
auto → флаг не передаётся (дефолт runtime — auto, решает по шаблону).
Дефолт нового профиля — auto. Старые файлы (bool ReasoningChecked) мигрируются:
true → on, false → off (мостик обнуляется после миграции).
Имена флагов reasoning гуляют между билдами — флаги бюджета и его сообщения
лежат константами в одном месте (ReasoningBudgetFlag и
ReasonBudgetMessageFlag), правятся там. Бюджет и сообщение передаются
только при значимом значении и только при режиме on/auto (не off);
дефолт поля сообщения — стандартный текст в AppDefaults. Исключение:
при режиме on и бюджете 0 используется минимальный бюджет 1024
(AppDefaults.DefaultReasonBudgetMinimum), а не «без лимита».
Сообщение бюджета — редактируемый ComboBox: выбор из общего списка
(settings.json, раздел ReasonBudgetMessages) или ввод нового.
Редактирование списка: кнопка «...» рядом с комбобоксом открывает окно,
где можно добавить/удалить/изменить сообщение (удаление глобальное —
применяется ко всем моделям). Пустой список сидится стандартным текстом при загрузке.

## Грабли UI (чтобы интерфейс не «скакал»)

Поля проверяются ПОСЛЕ ввода (Enter или потеря фокуса): пока печатаешь —
курсор не дёргают; чушь/вылет за границы -> ближайшее безопасное число.
Ползунок контекста и поле синхронизированы без событий-петель.
(В WinForms-прототипе ради этого мучились с AutoSizeMode.GrowAndShrink и
TickFrequency — WPF это не касается.)

## Подсказки по тюнингу

0. Новая модель: сначала V100 ONLY (или RTX ONLY для небольших моделей).
   Затем SAFE V100+RTX. BALANCED и AGGRESSIVE включай только после
   стабильного прогона и с тем же набором уже открытых приложений.
   Не меняй GPU-нагрузку на лету.
1. Для агента сначала 32k context. 64k имеет смысл только когда нужен:
   большой ctx отъедает KV/RS/scratch и может вытолкнуть веса на CPU.
2. Q8, который физически не помещается в суммарную свободную VRAM,
   неизбежно получит CPU offload и может быть намного медленнее Q6/Q4.
3. -b влияет в основном на prompt processing, -ub на физический кусок batch
   и scratch. Дефолт 2048/512. Для V100 полезно БЕНЧМАРКОМ проверить
   ubatch 64/128/256/512/1024 — универсального победителя нет.
4. --cache-prompt включён сервером по умолчанию. --cache-reuse может заметно
   помочь агентам на повторяющихся длинных префиксах, но для ЧИСТОГО
   benchmark его лучше держать 0.
5. --sse-ping-interval 10–15 с помогает не оставлять HTTP/SSE соединение
   совсем немым во время долгого prefill. Если агент имеет СВОЙ жёсткий
   timeout, его всё равно надо увеличивать в настройках агента.
6. reasoning budget: 4–8k токенов в рутине, 16–32k в сложном коде; 0 в ЭТОМ
   UI = не передавать флаг (runtime использует свой default).
7. MTP может ускорить decode при хорошем acceptance, но расходует память.
   На пограничном Q8 сначала добейся стабильной работы БЕЗ MTP.
8. Sampling-параметры (temp, penalties и т.д.) — это ДЕФОЛТЫ СЕРВЕРА: их
   можно переопределить в каждом запросе. Для чистого benchmark держи общий
   переключатель sampling выключенным.

## Tool-calls / агентная работа (--jinja)

- Умеет ли модель вызывать функции, из GGUF не видно напрямую: это свойство
  chat-шаблона + серверного парсера + обучения модели. Сканер даёт
  прокси-оценку по двум сигналам:
  1. jinja-шаблон из GGUF (tokenizer.chat_template*) сканируется на
     обработку tools / tool_calls / tool_call_id / role==tool;
  2. словарь — на спец-токены вида `<tool_call>`, `[TOOL_CALLS]`.
- Вердикты: «да» (шаблон умеет tools), «нет» (шаблон без tools),
  «неизвестно» (шаблона нет — сервер подберёт встроенный по семейству).
- Практика: для агентов держи --jinja включённым — тогда сервер передаёт
  функции модели и парсит ответ в OpenAI tool_calls. Он включается
  автоматически при вердикте «да»; ручное переключение запоминается в
  профиле модели и авто-детектом не сбрасывается.
- Ограничения эвристики: шаблон может уметь tools, а модель — не уметь ими
  пользоваться (не обучена), и наоборот. Спорные случаи проверяй тестовым
  запросом с tools или карточкой модели на HF.

## Что добавлено в WPF-версии (v5)

- Мультимодальность: рядом с моделью (в папке модели) ищутся mmproj*.gguf;
  переключатель + выбор файла -> флаг --mmproj.
- Параметры разработчика (sampling): temp, top-k, top-p, min-p,
  repeat-penalty, repeat-last-n, presence/frequency-penalty, seed; общий
  выключатель «передавать в команду».
- Сохранение параметров между сессиями и перечитываниями моделей:
  settings.json рядом с exe, глобальные + по-модельные профили.
- Несколько корневых каталогов с моделями (окно «Настройки», открывается кнопкой в заголовке): список
  сохраняется в settings.json; кнопки Добавить/Удалить/Изменить; активный
  каталог используется при сканировании и загрузке.
- Алиас: регистр не трогается (GPT, UD и прочие аббревиатуры остаются как в
  имени файла).
- Отдельный блок «Строка запуска» + одна кнопка копирования.
- Размер файла модели (GGUF) и mmproj — на панели информации.
- Multi-file (split) модели: набор шардов <stem>-0000N-of-0000M.gguf в одной
  папке — одна запись каталога; в -m уходит первый шард 00001 (llama.cpp
  грузит split только через первый шард); метаданные — из шарда split.no == 0,
  тензоры со всех шардов, размер — сумма файлов. Нехватка шарда — явное
  предупреждение, а не тихое занижение.
- Строка «Квантование» в инфо о модели — квантование модели из GGUF
  (general.file_type), а не KV-кэша; при отсутствии ключа — оценка по
  body-весам с пометкой; bpw и распределение типов — в тултипе.
- Границы честности: у смешанных квантов (UD-*-XL, _L-варианты) часть весов в более
  точном типе, поэтому bpw выше эталона метки; у gpt-oss метка F16/Q8_0
  описывает не-экспертные веса, эксперты — mxfp4; неподдерживаемые оценщиком
  архитектуры (qwen4exp) этим не чинятся — нераспознанные байты показываются
  отдельно («не учтено N GiB»).
- Оценка распределения блоков между GPU (грубо; точную раскладку всё равно
  делает llama.cpp через --fit).
- Подсказки (tooltip) у каждого параметра: что делает, на что влияет, где
  документация. Ссылки в тултипах кликабельны: клик по тултипу проходит
  «насквозь» (так устроен WPF), поэтому его перехватывает
  Controls/ToolTipLinker и открывает браузер, если под курсором ссылка.
- Детект tool-calls (агентная работа): строка «Инструменты» в инфо о модели
  + авто --jinja; предупреждения о противоречиях.
